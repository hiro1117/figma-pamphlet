# パンフレット依頼票スキル

スキル版: 2026-10

仕様書などの資料を読み、パンフレット作成スキル `figma-pamphlet` に渡す**依頼票**を作る。資料は案件ごとに書き方が違う(仕様書・仕様整理書・議事録・メール・Excel の時刻表など)。項目名や章立てに頼らず、中身で拾う。

依頼票の目的は2つ:

1. `figma-pamphlet` の Step 1(ヒアリング)で聞く項目を先に埋め、聞き返しを「本当に決まっていないこと」だけにする
2. 表紙の絵(車両・地域の名所・利用者)を、あとで画像生成(Nano Banana など)に渡せる粒度で残す

## 参照ファイル

- `references/schema.md` — 依頼票 JSON(`pamphlet-brief/1`)の全項目・値の決まり・figma-pamphlet の Step 1 との対応。**JSON を書く前に必ず読む**
- `references/illustration.md` — 車両タイプの分類、地域の絵の拾い方、画像生成プロンプトへの組み立て方。**`illustration` を書く前に読む**
- `examples/sakaide.brief.json` / `examples/sakaide.brief.md` — 坂出市の仕様整理書(第9版)から作った見本。迷ったら形を合わせる

## 守ること

- **資料に無いことを書かない。** 電話番号・時刻・運賃・日付・サービス名・事業者名を推測で埋めない。見つからなければ `status: "要確認"`、値は `null`
- 例外は2つだけで、どちらも `status: "推測"` を付ける。①地域の名所・地形の候補(一般知識から出してよいが、リーダーの確認が要る)②キャッチコピーなど文言の草案(`status: "草案"`)
- **住民向けの情報だけを拾う。** 契約・支払・見積・端末台数・アカウント数・データ所有権・保守体制・社内の担当者名は依頼票に入れない(個人名は一切書かない。事業者名・自治体名は書く)
- **「現行」と「導入後」を分ける。** 資料が現行の運用(電話予約の締切など)と、システム導入後の運用を書き分けているときは、パンフレットに載せるのは**導入後**。導入後が協議中なら、現行の値を `note` に残して `status: "協議中"` にする
- **新しい版・訂正を優先する。** 版の履歴・訂正依頼(「〜を訂正」「〜に変更」)があれば最新を採る。食い違いは `conflicts` に両方の値と出所を残す
- 各値に**出所**(`source`: 資料名と章・表・日付)を付ける。あとで人が確かめられるように

## Step 1: 資料を受け取る

1. 添付・貼り付け・ファイルパス・Drive のどれでもよい。複数あれば全部読む。Word・PDF・Excel は該当するスキル(docx / pdf / xlsx)で中身を出してから読む
2. 資料の一覧を作る: 名前・版・作成日/改訂日。改訂の注記(例「第9版・南エリア予約締切16時・下り12:00発を反映」)は必ず控える
3. 自治体のホームページ(運行案内・時刻表・運賃表・乗降場所)の URL をもらったら、リンク先のエリア別ページまで読む。時刻表・運賃表・乗降場所一覧は画像のことが多いので、画像を開いて読み取り、`source` に「画像から読み取り」と書く。埋め込みの Google マイマップは `https://www.google.com/maps/d/kml?mid=<mid>&forcekml=1` で KML を取れば、乗降場所の名前と座標が得られる(一覧画像と件数を照合する)。公表済みのホームページと社内資料が食い違えば、公表値を採って `conflicts` に残し、確認の質問を1つ入れる
4. 資料が明らかに足りない(運行区域も時刻も無いなど)ときは、ここで「〇〇の資料はありますか?」と1回だけ聞く。足りないまま進めてよければ、足りない項目を全部「要確認」にする

## Step 2: 抜き出す

`references/schema.md` の順に埋める。とくに次は取りこぼしやすい。

- **区域が複数ある**(東北/東南/南エリア など): `service.areas[]` にエリアごとに分けて書く。時刻・予約締切・利用できる区間(区域外の乗降場所へ行けるか、乗り継ぎ)はエリアで違うことが多い
- **時刻表**: 便ごとに発時刻と発地を書く。上り・下りは資料の呼び方のまま。「予約のない便は運行しない」のような運行ルールは `rules[]` へ
- **予約**: 電話とアプリ(LINE)を分け、それぞれ「何日前から」「いつまで」「受付時間」。電話番号は資料の表記のまま、受付開始日も
- **運賃**: 方式(ゾーン制・定額・距離制)・金額・区分(大人/小児/高齢者/障がい者/市民など)・支払いの時点と方法。金額が無いことはよくある → 要確認
- **開始日・事前登録**: 本運用開始日、試験運行、利用者登録の受付開始。「〜案」「予定」「概ね了承」は `status: "予定"`
- **乗降場所**: 一覧があれば `stops` に。無ければ乗降スポット表を作れないので要確認に載せる
- **周知の方針**: 配布のしかた(全戸配布・自治会・窓口)、部数、配布時期。何を作るか(冊子/単票、エリア別か共通か)の判断材料になる
- **車両**: 車種・定員・台数・車体色・事業者名。`references/illustration.md` の分類に当てる

## Step 3: 絵の材料を整理する

`references/illustration.md` に従って `illustration` を埋める。

1. **車両**: 資料の表記(「セダンまたはジャンボタクシー」)をそのまま残し、分類(`sedan` / `jumbo` など)に当てる。複数ならすべて並べ、表紙に描く1台を `cover_pick` で提案する(理由も)。車体色・行灯・ラッピングは資料に無ければ要確認
2. **地域**: 運行区域の町名から、地形(海沿い/山あい/田園/町なか)と暮らし(買い物先・通院先・駅)を拾う。行き先に出てくる店・駅・病院は資料にあるので `確定`。名所の候補は一般知識から2〜4個出し、`推測` にして「運行区域の中にあるか」「住民に身近か」を理由に添える
3. **利用者像**: 資料の読み手と用途(高齢者の買い物・通院、乗り継ぎなど)から1〜2人分

## Step 4: 聞き返しを絞る

`open_questions[]` に、要確認・協議中・推測の項目から**パンフレットが作れない順**に並べる。

1. 作業が止まるもの(`blocking: true`): サービス名(題字)、電話番号、導入後の予約締切、開始日、運賃の金額、乗降場所の一覧(スポット表を作る場合)、生成AIのイラストを使ってよいか
2. 作れるが印刷前に要るもの: 受付時間、LINE の QR・ロゴ・地図の素材、車体の見た目
3. 表紙の絵の確認: 名所の候補、車両の選び方

質問は相手(リーダー・営業担当)が答えやすい言い方にし、選択肢があれば添える。1回に出すのは**7問まで**。残りは「ほかに〇件あります」とまとめる。

## Step 5: 出力する

1. ファイル2つを作る(ファイルを作れない環境では会話にそのまま出す)
   - `<案件名>_依頼票_<YYYYMMDD>.md` — 人が読む版。構成は見本 `examples/sakaide.brief.md` と同じ: ①案件の要点(3行)②決まっていること ③聞きたいこと ④表紙の絵の材料 ⑤資料の出所
   - `<案件名>_依頼票_<YYYYMMDD>.json` — `pamphlet-brief/1`。figma-pamphlet が読む版
2. 会話では、要点3行と「聞きたいこと」だけを出し、ファイルを渡す
3. 最後に次の手順を1行で伝える: 「答えが揃ったら、この依頼票を添えて『Figma でパンフレットを作って』と依頼してください」
4. 答えをもらったら JSON を更新し(`status` を `確定` に、`source` に「〇月〇日 回答」)、`meta.revision` を1つ上げて出し直す

## 完了前チェック

- [ ] 個人名・契約金額・支払条件が入っていない
- [ ] 電話番号・時刻・運賃・日付に、資料に無い値が入っていない(`推測` は名所と草案だけ)
- [ ] 訂正・新しい版の値を採っている(`conflicts` に古い値)
- [ ] エリアが複数なら、エリアごとに時刻と予約締切が分かれている
- [ ] 「現行」の値を導入後として `確定` にしていない
- [ ] 車両が資料の表記のまま残り、分類が付いている
- [ ] `open_questions` が「止まる順」で、7問以内に絞ってある
