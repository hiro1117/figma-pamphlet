# パンフレット生成パイプライン改善計画書 (v1, 2026-09-24)

前提: 作者Hiroは群馬の副業Webエンジニア。Cicac社の地域乗合タクシー(MITT)紹介パンフレット(A4冊子 表紙+中面、高齢者70代中心の読み手)を、Figma MCP(use_figma / upload_assets / get_screenshot)とカスタムスキル「figma-pamphlet」(2026-08-20版)で作っている。実利用者はFigmaもClaudeも初めてのコールセンターのオペレータ(Claude web + Figmaコネクタ)。Hiroは週1勤務のため伴走不可。現行スキルの要点: テンプレ複製→色(1色相濃淡の2群置換)→文言→素材(利用者持ち込み、全点使用)の順、面付け寸法1691×2392px厳守(A4=約8.05px/mm)、フォント欠損時はNoto Sans JP代替、完了前チェック6項目、「フォント・サイズ・レイアウトは変えない(差し替え専用)」ルール、design-rulesに可読性基準(高齢者: 本文12〜14pt、行間1.6〜1.8、コントラスト7:1)と表現指針(暖色背景・袋文字・傾いた帯・人物イラスト1体以上)。Figma MCPには現在 Weave 連携ツール(weave_find_model / weave_run_model: 画像モデルを直接実行、実行ごとに費用承認)があるが、Figmaアカウントは未リンク(2026-09-24時点)。

## 1. 目的と成功基準

figma-pamphletの叩き台を「修正前提の下書き」から「初見で『おっ』と言わせる完成度70%の初稿」に引き上げる。驚きの源泉はキービジュアルと、それに整合した色・書体・装飾なので、その3点を画像モデルで先に決め、組版側に正確に流し込む。

| # | 基準 | 目標値 | 測り方 |
| --- | --- | --- | --- |
| S1 | 独立LLM評価者の5項目ルーブリック平均 | 4.2/5以上、3未満の項目なし | フェーズDの評価者JSON |
| S2 | 人間ブラインドA/B(現行スキル出力 vs 新パイプライン出力) | 新版選好率70%以上 | Cicacメンバー3名以上、案件3件 |
| S3 | 決定的チェック(印刷・可読性)の残存Fail | 0件 | フェーズD第1層の出力 |
| S4 | 1案件の叩き台所要時間(オペレータ運用) | 現行の1.3倍以内 | 開始〜引き渡しの実測 |
| S5 | 追加コスト(画像生成) | 1案件あたり300円以内 | モデルの課金ログ |

S1とS3は自動で毎回測る。S2は最小実験(11章)で1回測り、以後は四半期ごとに再測する。

## 2. 現状と課題

現行スキルは「壊れない叩き台」は達成。驚きに欠ける原因5つ(安全側設計の裏返し):

| # | 原因 | 現行の該当ルール | 影響 |
| --- | --- | --- | --- |
| C1 | 骨格が毎回同じ | Step 2「テンプレートを複製してから編集する」 | 差分が色と文言だけになり「見たことがある」印象 |
| C2 | キービジュアルが存在しない | 「利用者が商用利用可サイトから選んだ素材を全点使う」 | 紙面を支配する1枚がなく、雰囲気の異なる小イラストが並ぶ |
| C3 | 色が1色相の濃淡のみ | 「メイン1色相の濃淡モデル」 | 安全だが単調。アクセントは指定時のみ |
| C4 | 表現ルールが発動しない | design-rules「袋文字・傾いた帯・多色タイトル」 vs 「フォント・サイズ・レイアウトは変えない」 | 差し替え専用ルールが優先され装飾が追加されない |
| C5 | 検証が「崩れの有無」だけ | Step 4「文字あふれ・重なり・余白潰れを目視確認」 | 美的水準の判定基準がなく、平凡でも合格 |

変えるのは「見出し・装飾・色・イラスト」の層だけ。「本文・寸法・折り位置」は不変。

## 3. パイプライン全体像

原則: 驚きは画像モデルに、正確さは組版に、判定はコードと独立評価者に分担。

A. ムード案生成(Nano Banana Pro 3〜4案) → 利用者が1案選ぶ → B. トーン言語化(tone.json) → C. 組版(Figmaテンプレ+装飾+イラスト) → D-1 決定的チェック(Fail→Cへ戻る) → D-2 LLM評価者5項目採点(未達→Cへ) → 引き渡し。ループ最大3周、最良スコアの周を採用。

| フェーズ | 担当 | 入力 | 出力 | 人の関与 |
| --- | --- | --- | --- | --- |
| A | Nano Banana Pro(Figma Weave経由 or Gemini) | 案件ブリーフ、完成見本スクショ | 表紙コンセプト画3〜4案(2K) | 1案を選ぶ |
| B | Claude(視覚読み取り) | 採用案の画像、案件ブリーフ | tone.json | 確認のみ |
| C | Claude + use_figma / upload_assets | tone.json、テンプレ、素材 | 制作物フレーム(表紙+中面) | なし |
| D | preflight.js(コード) + 評価者エージェント | 制作物フレーム、tone.json | 合否JSON、修正指示 | 合格後に確認 |

成果物はすべてFigmaファイル内に残す(案は素材ページ、tone.jsonは制作物フレームの説明欄)。

## 4. フェーズA: キービジュアル・ムード案生成

生成するのは「イラスト素材」ではなく「表紙1面まるごとのコンセプト画」3〜4案。文字は仮置き、最終文字はFigmaで組む。

実行経路:
| 経路 | 使う場面 | 前提 | 長所 | 短所 |
| --- | --- | --- | --- | --- |
| A1. Figma MCPのWeave(weave_find_model→weave_run_model) | オペレータ運用の本線 | FigmaアカウントとWeaveの連携、Weaveクレジット | チャット内で完結、費用承認の仕組みあり | 未連携、モデルの有無と単価は要確認 |
| A2. Gemini API(gemini-3-pro-image) | Hiro運用・一括生成 | APIキー、Claude Code | 4案並列、参照画像14枚まで、2K/4K | オペレータには渡せない |
| A3. Geminiアプリで手動生成→素材ページへ | A1が使えない時 | Google AI Pro等 | 準備不要 | 手作業 |

プロンプト構造(ブリーフ駆動): 1.役割(地域交通の高齢者向けパンフのアートディレクター) 2.案件(地域名・サービス名・事業者・読み手70代と家族・ゴール行動LINE登録/電話補助) 3.必須要素(顔のある人物イラスト1体以上・乗合タクシー車両・地域モチーフ1つ・受話器/LINEアイコン) 4.トーン軸(案ごとに1つ: (a)あたたかい手描き (b)爽やか (c)信頼・公的 (d)にぎやか) 5.制約(A4縦、余白広く、文字少なく大きく、写実禁止、紫→青グラデ禁止、英字多用禁止、細い明朝禁止) 6.参照(完成見本スクショ1〜2枚、指定色) 7.出力(2K、日本語仮文言)。

案の提示と選定: 4案をupload_assetsで素材ページの案件グループに並べ番号を振る → get_screenshotで1枚にして番号で選んでもらう → 選定観点3つ(読み手適合/何をすればよいかが一目で分かるか/印刷で濁らない色か) → 不採用案は「案」サブグループに残す。

注意: 出力はラスターで文字は崩れることがある。案の人物・車両はフェーズCで切り出し候補(背景除去はNano Banana Proの編集指示)。SynthIDウォーターマークあり、自治体案件では「AI生成画像を使用」と説明できるようにする。

## 5. フェーズB: トーンの言語化(tone.json)

採用案の画像を「組版が実行できる仕様」に翻訳し、形容詞をhex値・フォント名・寸法・数量に落とす。

スキーマ例:
```
{ "direction": {"label":"あたたかい手描き","one_liner":"クリーム地に朱色の帯、丸ゴシックの大見出し"},
  "palette": {"main":"#D9542B","main_light":"#F6D6C8","accent":"#2E7D5B","paper":"#FBF6EE","ink":"#231815"},
  "typography": {"headline_family":"Zen Maru Gothic","headline_weight":"Black","body_family":"Noto Sans JP","jump_ratio":3.2,"headline_treatment":"white_outline_shadow"},
  "decoration": {"signature_element":"tilted_band","shapes":["rounded_rect","speech_bubble"],"background":"cream_with_sky_gradient_top"},
  "illustration": {"style":"flat_vector_thick_outline","line_weight":"thick","palette_usage":"main+accent+skin","subjects":["elderly_woman_on_phone","shared_taxi_van","mountain_silhouette"]},
  "mood_words": ["あたたかい","手を差し伸べる","ご近所"],
  "avoid": ["purple_blue_gradient","thin_mincho","photo_realism","english_heavy"],
  "layout_hints": {"hero":"top_60pct","cta":"bottom_right","person_faces":"toward_cta"},
  "confidence": {"palette":0.9,"typography":0.6,"illustration":0.8} }
```

抽出手順: 1.画像+ブリーフを渡し「見えるものだけ記述、見えないものは推測せずconfidenceを下げる」で初稿 2.正規化(palette.main/main_lightは既存の濃淡2群置換へ、accentは新設。headline_familyはFigmaアカウントの和文フォント許可リスト(Noto Sans JP / Zen Maru Gothic / Zen Kaku Gothic / M PLUS Rounded 1c 等)へマッピング。signature_elementは1つだけ) 3.利用者にはJSONを見せず1文で確認 4.確定tone.jsonをフレーム説明欄(node.description)と素材ページの案件グループ(テキストノード)に保存。

illustration節から「イラスト生成ブリーフ」を派生。subjectsは人物1体以上・ゴール行動をしている姿・定番アイコンを必ず含める。

## 6. フェーズC: スキル注入と組版

スキル改訂点(2026-10版):
| 場所 | 現行 | 改訂 |
| --- | --- | --- |
| Step 1.5 カラー決定 | 色見本チップ2〜3案 | フェーズA(ムード案4案)に置換。色はtone.jsonから |
| 新Step 1.7 | なし | トーン確定(1文確認、説明欄に保存) |
| 差し替えの約束事 | フォント・サイズ・罫線・レイアウトは変えない | 本文・寸法・折り位置は不変。見出しフォント・見出し色・装飾レイヤー・イラストはtone.jsonで変える |
| カラー適用 | 濃淡2群置換、アクセントは指定時のみ | 濃淡2群 + accentを電話番号・CTA・バッジの限定3箇所に |
| design-rules デザイン表現 | 表現の一覧 | signature_element / headline_treatmentで発動条件を決める。1紙面にsignatureは1つ |
| 新規 references/keyvisual.md | なし | フェーズA・B手順、プロンプト、フォントマッピング表、イラスト経路 |
| 新規 references/preflight.md | なし | フェーズD決定的チェック仕様とスクリプト |

tone.json→Figma操作変換表: palette.main/main_light→2群一括置換(IMAGE fillは対象外) / accent→`#`付き電話番号・CTA・バッジのfillのみ / headline_family→`#見出し`系レイヤーのfontNameを許可リスト内で置換(本文不変) / white_outline_shadow→stroke(白・OUTSIDE・フォントサイズの6%)+Drop Shadow / tilted_band→createNodeFromSvgで帯1本、rotation −4°、文字より背面 / background→フレームfillをpaper色、上部に空グラデ矩形(折り位置をまたがない) / subjects→イラスト経路で生成し`#イラスト`プレースホルダへ。

イラスト投入経路: I1 採用案からの切り出し(Nano Banana Pro編集で背景透過→upload_assets PNG→`#イラスト`ノードfill; キービジュアル・人物) / I2 Recraft V4 Styles Vector(I1をスタイル参照にsubjectsをSVG生成→upload_assets SVG→編集可能ベクター; ワンポイント・アイコン群) / I3 利用者持ち込み(従来。tone.jsonに合わないものは理由を添えて外す提案)。

Figmaが本線(印刷入稿・テンプレ資産・オペレータ手直し)。HTML組版(proposal-collateral系)は同じtone.jsonを読ませ「トーン検証プレビュー」と「Web配布用縮小版」の副線。

## 7. フェーズD: 自己検証(二層ハーネス)

第1層 決定的チェック(preflight.js、use_figmaで実行): Pass/Failと該当ノードID・実測値・修正案をJSONで返す。しきい値はフレーム実寸からpx換算(冊子1691×2392は約8.05px/mm、1pt≈2.84px。乗降スポット表794×1123は約3.78px/mm。必ずフレーム幅÷210mmで係数算出)。

| # | チェック | しきい値(高齢者向け) | 判定方法 |
| --- | --- | --- | --- |
| P1 | フレーム寸法 | 基準寸法と完全一致 | width/height照合 |
| P2 | 本文フォントサイズ | 12pt以上(約34px) | TEXTのfontSize走査、注記は10pt |
| P3 | 文字あふれ | 0件 | クローンをWIDTH_AND_HEIGHTにして元枠と比較 |
| P4 | コントラスト比 | 7:1以上(本文)、大見出し4.5:1 | 文字fillと直近背景fillから相対輝度 |
| P5 | 塗り足し | 背景要素が仕上がり端から3mm(約24px)外まで | 背景・裁ち落とし要素の絶対座標 |
| P6 | 折り位置の安全域 | 文字が折り線から8mm(約64px)以上 | 折り線y=高さ/2との距離 |
| P7 | 仮置き文言 | 0件 | `0000` `〇〇` `(仮)` `ダミー` を正規表現 |
| P8 | フォント許可リスト | 逸脱0件 | fontName.family照合 |
| P9 | 禁止色 | 0件 | 紫→青グラデ、tone.jsonのavoid |
| P10 | 人物イラスト | 1体以上 | `#人物`プレースホルダにfillがあるか |
| P11 | QRコード寸法 | 2cm角以上(約161px)+周囲余白 | `#QR`ノード寸法と隣接距離 |
| P12 | 電話番号の視認性 | 本文の3倍以上 | `#電話`のfontSize/本文中央値 |

出力はuse_figmaの20KB返却上限に収まるようFailのみ返す。

第2層 LLM評価者(別コンテキスト): 入力=get_screenshot(長辺1568px)、tone.json、ブリーフ、ルーブリック、完成見本の採点済み実例3〜5枚(few-shot)。評価者は執筆側の思考・履歴を見ない。オペレータ運用ではサブエージェント不可のため「評価モード」依頼文を新規チャットに貼る運用で代替。出力=5項目1〜5点+根拠、上位3件の修正指示(ノード名)、AIスロップ該当有無。

| # | 項目 | 5点 | 1点 |
| --- | --- | --- | --- |
| R1 | 親しみやすさ | 70代が手に取りたくなる温かみ、顔のある人物が主役 | 事務的、威圧的、人物なし |
| R2 | 伝わりやすさ | 「何をすればよいか」が0.5秒で分かる | CTAが埋もれる |
| R3 | 独自性(非スロップ) | 地域と案件の固有性が見える | どの地域でも同じ |
| R4 | クラフト | ジャンプ率・余白・整列・色数(3色以内)が整う | 密集、色が散る |
| R5 | 一貫性 | tone.jsonの方向・色・書体・イラスト調が一致 | 素材のトーンが混在 |

合格: 平均4.2以上かつ3点未満なし。

ループ制御: 1.組版→第1層(Failは修正して再実行、最大3回。残るFailは手作業へ) 2.Pass→スクショ→第2層 3.上位3件修正→第1層から 4.最大3周。各周のスクショとスコアを状態JSON(/tmp/pamphlet-state-{案件}.json またはフレーム説明欄)に保存し最良スコアの周を採用 5.打ち切り時は残指摘をStep 5引き渡しリストへ。

## 10. コスト・ライセンス・リスク

1案件の追加コストは約200〜400円(4案+編集2回+ベクター10点)。Weaveクレジット換算は連携後に実測。

| 同 編集(切り出し・背景透過) | 同上 | 2〜3枚 | 約50円 |
